# Стандарты кода lib-local-rag

Правила для любой правки в `src/`, `main.py`, `mcp_server.py`, `scripts/` и `tests/`.
Это эвристики, а не догмы: если правило делает конкретное место запутаннее, оно здесь
неприменимо. Ограничения сборки и запуска («грабли») описаны в `AGENTS.md` и имеют
приоритет над этим файлом.

## 0. Главное для этого проекта

- **Рабочий код не ломать.** Любая правка поведения — с регресс-тестом и полным прогоном
  `uv run pytest -m "not integration"`, результат не хуже базовой линии.
- **Метрики поиска — критерий.** Правка, ухудшившая A/B-замер качества поиска, откатывается.
- **Грабли из `AGENTS.md` не трогать** (batch_size, `PerformanceMode.LATENCY`,
  `DEFAULT_INFERENCE_STREAMS`, `_ov_token_len` через `count_tokens`, `ConditionUser` в юнитах,
  сборка `.deb` только через `make deb`).
- **Согласованность важнее вкуса.** Новый код пишется так же, как окружающий.

## 1. Именование

- Имя отвечает на вопрос «что это» без чтения реализации: `active_paths`, а не `data2`.
- Длина имени — по области видимости: `i` в коротком цикле нормально, поле класса `i` — нет.
- Функции — глаголы (`build_index`), классы и переменные — существительные (`LanceWrapper`),
  булевы — вопросы (`is_enabled`, `has_text`).
- PEP 8: `snake_case` для функций и переменных, `PascalCase` для классов,
  `UPPER_CASE` для констант модуля.
- Без магических чисел и строк: значение выносится в именованную константу
  (`DEFAULT_INFERENCE_STREAMS = 2`) или в конфиг.
- Один термин на одну сущность во всём проекте (чанк, документ, путь, индекс —
  не смешивать синонимы).
- Тип не кодируется в имени (`str_name`, `list_items`) — для этого есть тайп-хинты.

## 2. Функции

- Одна функция — одна задача. Если в описании появляется «и», её пора делить.
- Ориентир — до ~30 строк и вложенность не глубже 2–3; лечится ранними выходами и
  выделением подфункций.
- До 3–4 аргументов; больше — dataclass/pydantic-модель параметров.
- Без булевых флагов-переключателей поведения (`process(True)`): лучше две функции
  или именованный keyword-аргумент.
- Один уровень абстракции: не смешивать логику ранжирования с запросами к LanceDB
  и форматированием ответа.
- Функция либо меняет состояние, либо возвращает результат (CQS), без скрытых побочных
  эффектов. Чистые функции предпочтительнее — их проще тестировать.

## 3. Комментарии и документация

- Комментарий объясняет **почему**, а не **что**. Коротко и по делу.
- Без истории правок в комментариях («Раньше…», «Шаг N», цифры замеров) — это место
  для сообщения коммита и `docs/`.
- Комментарий, противоречащий коду, исправляется по коду. Если комментарий вскрыл
  ошибку — чинится код.
- Закомментированный код удаляется — история есть в git.
- Документируются публичные API (ручки FastAPI, инструменты MCP), неочевидные
  алгоритмы и обходные решения (со ссылкой на дефект/задачу).

## 4. Структура и архитектура

- **DRY** — не дублировать *знание*. Случайное совпадение кода — не повод для абстракции:
  преждевременная абстракция хуже копипасты.
- **KISS** — простое решение почти всегда лучше умного.
- **YAGNI** — без функциональности «на будущее».
- **Разделение ответственности:** HTTP (`src/server`), индексация (`src/indexer`),
  парсинг (`src/parsers`), конфиг (`src/config.py`) живут отдельно; бизнес-логика
  не зависит от FastAPI и HTTP.
- **Низкая связанность, высокая связность:** модуль знает о других минимум.
- **Закон Деметры:** без цепочек `a.b.c.d` через чужую структуру.
- **Композиция вместо наследования.**
- **Инкапсуляция:** детали реализации — с `_`, наружу узкий интерфейс.
- **SOLID:** одна причина для изменения у класса; расширение без правки
  существующего кода (например, новый парсер — через реестр `src/parsers`);
  наследник подставляется без сюрпризов; узкие интерфейсы; зависимость от абстракций.

## 5. Данные и состояние

- Предпочитать неизменяемость; разделяемое изменяемое состояние между потоками
  и корутинами — только с явной синхронизацией (OpenVINO InferRequest, LanceDB).
- Единый источник истины: настройка живёт в конфиге, а не дублируется в коде.
- Валидация на границах (pydantic-модели запросов API, конфиг при загрузке),
  внутри — с доверенными данными.
- Тайп-хинты на всех новых функциях; невалидные состояния — невыразимы через типы.
  Исключение — stdlib-скрипты для системного python3 (`mcp_server.py`,
  `scripts/register_mcp.py`, `scripts/sberos_check.py`): они держат совместимость
  со старым python3 и пишутся без аннотаций, как весь файл.
- Без скрытых глобальных переменных и зависимостей от порядка вызовов.

## 6. Обработка ошибок

- **Fail fast:** падать рано и громко, не тащить некорректное состояние дальше.
- Не глотать исключения: `except Exception: pass` запрещён; если ошибка
  допустима (битый файл при индексации) — логировать с контекстом и идти дальше осознанно.
- Ожидаемые ошибки (невалидный запрос, файла нет) — часть контракта API
  (`HTTPException` с понятным кодом); баги локально не ловить.
- `None` по умолчанию не возвращать там, где уместны пустая коллекция или исключение.
- Сообщение об ошибке — с контекстом: что, где, с какими данными (без секретов и
  содержимого писем).
- Ресурсы — через `with` / `async with`, не вручную.

## 7. Тестирование

- Каждый исправленный баг сначала фиксируется тестом.
- Много быстрых юнит-тестов (без OpenVINO, на заглушках), интеграционные —
  под маркером `integration`.
- Структура AAA: Arrange → Act → Assert; один тест — одна мысль.
- Тестировать поведение (контракт), а не реализацию.
- Тесты детерминированы и не зависят от порядка запуска.
- Код тестов — по тем же стандартам, что и рабочий код.

## 8. Масштабируемость

**Кодовая база:**
- Модули с явными границами и контрактами.
- Конфигурация — в `cfg/*.yml` и переменных окружения (`RAG_*`), не в коде.
- Хороший тест границ — фичу можно удалить, не задев остальное.

**Нагрузка (локальный демон на АРМ):**
- Долгие операции — асинхронно и через очередь (`persist-queue`), без блокировки
  event loop.
- Идемпотентность операций индексации (повторная обработка файла не плодит дубли).
- Лимиты везде, где возвращается коллекция (`top_k`, размер чтения файла).
- Память и CPU ограничены рабочим местом: без загрузки всего индекса или файла
  в память без необходимости.
- **Сначала измерять, потом оптимизировать** — на целевом АРМ (x86), не на M1.

## 9. Процесс и инструменты

- Окружение — только `uv`; перед коммитом `make ruff` и `make tests`.
- Маленькие атомарные коммиты с осмысленным сообщением на русском.
- Логирование через `get_logger(__name__)` / `logging`, с уровнями; в логах нет
  секретов, токенов и персональных данных (содержимого документов и писем).
- Версии зависимостей фиксируются в `uv.lock`; новые зависимости — только
  при реальной необходимости (их тянет PyInstaller в сборку).
- Секреты (`.secret`, токены) в репозиторий не попадают.
- Отвергнутые эксперименты в git не коммитятся.

## 10. Поддержка кода во времени

- Правило бойскаута: оставлять код чище, чем нашёл — небольшими порциями и только
  с тестами.
- Технический долг — осознанно: с записью, причиной и планом возврата.
- Мёртвый код удаляется сразу.
- Запахи кода, на которые реагировать: длинные функции и классы, длинные списки
  параметров, дублирование, методы, «завидующие» чужим данным, циклические
  зависимости, класс-бог, обилие флагов и `if`-каскадов по типу.

## Итог

1. Код читают чаще, чем пишут — оптимизировать под читателя.
2. Сложность локализуется: хорошее изменение затрагивает одно место.
3. Единый стиль проекта важнее личных предпочтений.
