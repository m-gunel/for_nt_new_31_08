# Установка и проверка пакета `.deb` (LocalRAG + MCP-мост)

Документ из двух частей.

- **Часть A — протокол проверки для тестировщика.** Четыре шага, никаких
  диагностических команд. Всё, что нужно знать о состоянии, пакет сообщает сам
  в выводе установки.
- **Часть B — справочник для сопровождающих.** Что ставит пакет, где логи, как
  проверять по частям. Тестировщику эта часть не нужна.

Пакет: `lib-local-rag_1.0.10_amd64.deb`.

---

# Часть A. Протокол проверки

Выполнять только шаги ниже. Если что-то пошло не так, ничего не чините и
никаких команд не запускайте, а пришлите то, что перечислено в разделе
«Если что-то не так».

## Шаг 1. Установить

```bash
sudo dpkg -i lib-local-rag_1.0.10_amd64.deb
```

- **Поверх 1.0.6 ставится той же командой.** Удалять старую версию заранее
  не надо: новая сама исправит то, что осталось от 1.0.6.
- Если dpkg откажет из-за проверки подписи, ставьте так же, как ставили 1.0.6:
  `sudo dpkg --no-debsig -i lib-local-rag_1.0.10_amd64.deb`.
- При обновлении с 1.0.6 dpkg может предупредить, что сценарий удаления
  старой версии завершился с ошибкой и вместо него взят сценарий из нового
  пакета. Это нормально, установка продолжится.
- **Если стояла 1.0.7 или раньше и индекс уже собран**, его схема с 1.0.8
  несовместима: после установки сбросьте индекс один раз (папки сохранятся),
  он соберётся заново:
  `curl -X POST "http://127.0.0.1:$(cat ~/.files-search/port)/api/v1/reset?keep_config=true"`.
- **С 1.0.8 на 1.0.9** сброс не нужен: карточки документов дописываются в
  индекс при старте. В 1.0.9 limit поиска — число документов, а не чанков.
- **С 1.0.9 на 1.0.10** сброс не нужен: индекс тот же, меняется только поиск.

## Шаг 2. Прочитать итог установки

Пакет сам сообщает, что сделал. В выводе установки должно быть:

1. Блок **«LocalRAG: пользователь <ваш логин> (uid …)»**. В нём:
   - строки регистрации MCP с путями к конфигам: `записано: …/.wsc/config/wsc.json`
     и `записано: …/.gigacode/settings.json`. Вместо «записано» может стоять
     «без изменений», если запись уже была;
   - итоговая строка вида `-> демон запущен, индексация стартует после прогрева
     (~45 c); регистрация MCP выполнена`.
2. Общий текст: «LocalRAG 1.0.10 установлен и включён для всех пользователей»,
   «Индексация стартует автоматически…» и просьба перезапустить Workspace
   Computer и GigaCode.
3. Ближе к концу **«Итог по пользователям:»** и та же строка по вашему логину:
   «демон запущен…; регистрация MCP выполнена».

Если в итоге по вашему логину вместо «регистрация MCP выполнена» написано
«агенты (WSC, GigaCode) в домашних каталогах не найдены…», пакет установился,
но ни Workspace Computer, ни GigaCode у вас не установлен, и регистрировать
MCP-сервер было некуда. Для проверки нужен установленный агент: установите
Workspace Computer и GigaCode и повторите протокол с шага 1.

При установке поверх 1.0.6 в начале могут быть две строки, и это нормально:
пакет исправил следы 1.0.6.

- «LocalRAG: /etc/lib-local-rag/distro.yml от сборки 1.0.6 не был объявлен
  конфигурационным файлом; сохранён как …distro.yml.localrag-old, ставится
  новый»;
- «LocalRAG: исправлены права, оставшиеся от предыдущей сборки» со списком
  путей.

Чего в выводе быть **не должно**:

- строк, начинающихся с **«LocalRAG: ВНИМАНИЕ»**;
- строк со словом **«ОШИБКА»**, в том числе итога **«регистрация MCP с
  ОШИБКАМИ»**;
- «не загружен», «демон НЕ запущен», «НЕ запустился», «регистрация MCP НЕ
  выполнена», «could not be found»;
- «пропуск: … не установлен в /home/sigma.sbrf.ru@<ваш логин>» у Workspace
  Computer или GigaCode, если этот агент у вас установлен. Такая же строка для
  папки разработчика `/home/work/…` — норма: там агент может быть не установлен;
- сообщений про `/activate` или «индексация не запущена».

Если есть что-то из этого списка, дальше не идите, см. «Если что-то не так».

## Шаг 3. Перезапустить агентов

Полностью закройте и снова откройте **Workspace Computer** и **GigaCode**.
Список MCP-серверов агенты читают только при запуске, без перезапуска новый
сервер они не увидят.

## Шаг 4. Вызвать поиск

В каждом из двух агентов попросите найти что-нибудь в ваших файлах, например:
«найди в моих локальных документах договор». Агент должен вызвать инструмент
`local_search` сервера `localrag`.

- Первый вызов может ответить, что **индексатор запускается или
  прогревается**. Это нормально: модели нужно около 45 секунд. Повторите через
  минуту.
- Ответ «Служба LocalRAG временно остановлена: идёт установка или обновление
  пакета» бывает, только пока идёт установка. Дождитесь её конца и повторите
  через минуту.
- Ответы «Индексатор LocalRAG не поднимается» и «служба … не найдена» — это
  сбой. Дальше не идите, см. «Если что-то не так».
- Пока идёт первый проход индексации, часть файлов может ещё не находиться, и
  мост об этом скажет. Первый проход по /home идёт в фоне: индексируются оба
  ваших каталога (`/home/sigma.sbrf.ru@<логин>` и `/home/work/…`) и всё в /home,
  что открыто вам на чтение.

## Критерий «готово»

1. MCP-сервер `localrag` виден **в обоих** агентах: и в Workspace Computer, и
   в GigaCode.
2. Первый вызов поиска даёт результат или ответ «индексатор запускается или
   прогревается», а через минуту повторный вызов даёт результат.
3. **После перезагрузки компьютера** всё работает без каких-либо действий:
   `localrag` на месте в обоих агентах, поиск отвечает (в первую минуту
   допустим ответ «прогревается»).

## Если что-то не так

Команд не выполняйте. Пришлите:

1. **Скриншот(ы) всего вывода установки** из шага 1, от команды `sudo dpkg -i`
   до конца. Особенно важны: блок «LocalRAG: пользователь …» целиком, все
   строки «LocalRAG: ВНИМАНИЕ» вместе со следующими за ними строками, «Итог по
   пользователям», строки «исправлены права», любые строки со словами
   «ОШИБКА», «ошибка», «error», «could not be found».
2. **Скриншот ответа агента** на вызов поиска. Если `localrag` в агенте не
   виден, то скриншот списка MCP-серверов агента.
3. Два факта: ставили поверх 1.0.6 или начисто; перезагружали ли компьютер
   после установки.

# Часть B. Справочник для сопровождающих

## 1. Что ставит пакет

| Путь | Что это |
|---|---|
| `/opt/lib-local-rag/main` | демон-индексатор (бинарь PyInstaller) |
| `/usr/lib/lib-local-rag/mcp/` | MCP-мост: `mcp_launcher.sh`, `mcp_server.py`, `register_mcp.py` |
| `/etc/lib-local-rag/distro.yml` | конфиг демона |
| `/usr/lib/systemd/user/lib-local-rag.service` | юнит демона |
| `/usr/lib/systemd/user/lib-local-rag-mcp-register.service` | регистрация MCP в конфигах агентов |
| `/usr/lib/systemd/user/lib-local-rag-mcp-register-wsc.path` | следит за конфигами Workspace Computer |
| `/usr/lib/systemd/user/lib-local-rag-mcp-register-gigacode.path` | следит за конфигом GigaCode |

Все юниты — **пользовательские** (systemd `--user`), а не системные: демон обязан
работать с правами владельца файлов. Поэтому он поднимается в **сессии
пользователя**, а не как глобальная служба.

Проверить, что системного экземпляра не завелось, а юниты читаются всеми:

```bash
dpkg -L lib-local-rag | grep systemd     # только /usr/lib/systemd/user/...
systemctl status lib-local-rag.service   # без --user: "could not be found", так и надо
ls -l /usr/lib/systemd/user/lib-local-rag*   # у всех -rw-r--r-- root root
```

«could not be found» **без** `--user` — норма: системного юнита нет. Та же
фраза в ответ на `systemctl --user status` — уже поломка, см. §7.

## 2. Установка

```bash
sudo dpkg -i lib-local-rag_1.0.10_amd64.deb
```

Только через `sudo`: dpkg пишет в `/usr`, `/etc` и `/var/lib/dpkg`. Всё
пользовательское `postinst` делает от имени пользователя, через `runuser`.

`postinst` по шагам (подробно — [debian/README.md §4](../debian/README.md)):

1. открывает для всех права своих каталогов и юнитов, если они закрыты (так
   лечится обновление с 1.0.6, где каталоги легли с 0700);
2. включает юниты для всех пользователей (вставка `dh_installsystemduser`);
   у root и системных учёток они не стартуют из-за `ConditionUser=!@system`;
3. в каждой открытой сессии делает `daemon-reload` и `restart` юнитов через
   приватный сокет пользовательского менеджера;
4. для тех же пользователей сразу прописывает MCP (`register_mcp.py --all`);
5. печатает итог по каждому пользователю.

Если открытых сессий нет (например, пакет ставится при сборке образа ОС),
демон и регистрация поднимутся при первом входе пользователя. Это задумано.

После установки агентов нужно перезапустить: конфиг MCP они читают на старте.

## 3. Проверить демон

```bash
systemctl --user status lib-local-rag.service
```

Ожидание: `Loaded: loaded (/usr/lib/systemd/user/lib-local-rag.service; enabled; ...)`
и `Active: active (running)`.

### Логи

```bash
journalctl --user -u lib-local-rag.service -n 200 --no-pager
```

> **Без `sudo`.** `sudo journalctl --user` открывает журнал того пользователя, от
> чьего имени запущен сам journalctl, — то есть журнал **root**, где нашего
> юнита нет и не будет. Вывод «-- No entries --» в этом случае не говорит ни о
> чём, кроме неверной команды.

Если и без `sudo` пусто, журнал пользователя может быть недоступен из-за
настроек journald на образе (`Storage=`, `SplitMode=`, `MaxLevelStore=`).
Тогда работают обходные пути:

```bash
journalctl _SYSTEMD_USER_UNIT=lib-local-rag.service -n 200 --no-pager
sudo journalctl -u "user@$(id -u).service" -n 200 --no-pager
systemd-analyze cat-config systemd/journald.conf | grep -Ev '^\s*(#|$)'
```

Независимо от journald демон **дублирует лог в файл**:

```bash
tail -f ~/.files-search/logs/lib-local-rag.log
```

Что должно быть в логе при нормальном старте, по порядку:

```
настройка памяти: ...
CONFIG_PATH=/etc/lib-local-rag/distro.yml | HOME=... | user_conf.yml=...
каталоги индексации: ...
порт NNNNN опубликован в /home/.../.files-search/port
pid NNNNN опубликован в /home/.../.files-search/pid
слушаю http://127.0.0.1:NNNNN (Swagger: http://127.0.0.1:NNNNN/docs) ...
прогрев модели OpenVINO: компиляция + два канала инференса
прогрев завершён за NN.N c
count total items for files
Application startup complete.
```

> Строки `Uvicorn running` в этом логе **нет и не будет** — это не поломка.
> `main.py` биндит сокет сам и передаёт его готовым (`run(sockets=[sock])`), а
> uvicorn печатает своё стартовое сообщение только когда открывает сокет
> самостоятельно. Ориентируйтесь на строку `слушаю http://...`.
>
> Обратите внимание на порядок: `порт NNNNN опубликован` появляется **сразу**, а
> прогрев идёт уже после. Между `слушаю ...` и `прогрев завершён` проходит 40-45
> секунд, и всё это время API не отвечает — так и должно быть.
>
> Индексация стартует сама, сразу после прогрева: строка `count total items for
> files` открывает первый проход. Дальше будет либо `collected N items, start
> indexing into files` и `begin indexing`, либо `nothing new for files` — ход
> виден в `GET /api/v1/status`. Строка про ожидание `POST /api/v1/activate`
> появляется только в отладочном режиме (`autostart_indexing: false`).

### Поднять уровень логирования

```bash
systemctl --user edit lib-local-rag.service
# [Service]
# Environment=RAG_LOGGING_LEVEL=DEBUG
# Environment=RAG_APP_LOGGING_LEVEL=DEBUG
systemctl --user restart lib-local-rag.service
```

`RAG_LOGGING_LEVEL` управляет корневым логгером и уровнем uvicorn,
`RAG_APP_LOGGING_LEVEL` — только логгером `app` (код индексатора).

### Важно про порт

Демон запускается с `RAG_PORT=0`, то есть **порт назначает ядро**, а не 8000.
Фактический номер демон кладёт в файл:

```bash
cat ~/.files-search/port        # например, 34981
```

MCP-мост читает порт **оттуда**, поэтому в конфиге агента адрес не прописан —
и это нормально.

## 4. Проверить, что API отвечает

```bash
PORT=$(cat ~/.files-search/port)
curl -s http://127.0.0.1:$PORT/api/v1/health     # {"status":"OK"}
```

Swagger UI — **в корне приложения**, а не под `/api/v1`:

```bash
xdg-open "http://127.0.0.1:$(cat ~/.files-search/port)/docs"
```

Для привычки ходить под префикс сделан алиас: `/api/v1/docs` ведёт туда же.

## 5. Индексация

Индексация **уже идёт**: демон в поставке стартует её сам (бесшовный режим),
команда activate не нужна. Ход первого прохода:

```bash
PORT=$(cat ~/.files-search/port)
curl -s http://127.0.0.1:$PORT/api/v1/status
```

Остановить на сессию — `POST /api/v1/deactivate`; состояние не персистится,
после перезапуска демона индексация возобновится сама.

Задать папки — через API, а не правкой YAML:

```bash
curl -X POST http://127.0.0.1:$PORT/api/v1/config \
  -H 'Content-Type: application/json' \
  -d '{"folders":["~/Документы"]}'
```

### OCR сканов в PDF

Страница PDF без текстового слоя, которую почти целиком занимает картинка
(скан), распознаётся встроенным в бинарь Tesseract. Языковые данные rus+eng
едут в пакете (`/opt/lib-local-rag/_internal/models/tessdata`), отдельный
tesseract ставить не нужно. Распознаёт отдельный процесс того же бинаря
(`main --ocr-worker`), по одному на файл, на одном ядре — поиск в это время
отвечает как обычно; ~1,5 с на страницу. Результат кэшируется в
`~/.files-search/ocr/`: повторная индексация и чтение файла через MCP
(`local_read_file`) заново не распознают. В журнале на файл — строка
`OCR <путь>: N стр. за X с`; если что-то не уложилось в лимиты —
одна строка WARNING «распознано N из M стр. (причина)».

Проверить воркер после сборки (страница 1 любого PDF; ответ — строка JSON
`{"page": 1, "text": "…"}`):

```bash
echo '{"path": "/путь/к/скан.pdf", "pages": [1], "dpi": 200, "language": "rus+eng", "tessdata": "/opt/lib-local-rag/_internal/models/tessdata"}' \
  | /opt/lib-local-rag/main --ocr-worker
```

Настройки — секция `ocr_cfg` конфига: `enabled`, `dpi` (200), `max_pages_per_file`
(200), `max_seconds_per_file` (1200). Выключить без правки YAML — в `[Service]`
юнита: `Environment=RAG_OCR_CFG={"enabled": false}`.

### Обновление с 1.0.7 и раньше

Схема индекса в 1.0.8 другая (метаданные документа и места фрагментов).
Индекс прежней версии надо сбросить один раз — список папок сохранится,
индексация начнётся заново:

```bash
curl -X POST "http://127.0.0.1:$PORT/api/v1/reset?keep_config=true"
```

## 6. Проверить MCP-мост

Мост — MCP-сервер поверх **stdio**: агент запускает его как подпроцесс, а не
через systemd. Проверить без агента:

```bash
echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  | /usr/lib/lib-local-rag/mcp/mcp_launcher.sh
```

В stdout придёт JSON со списком из **восьми** инструментов: чтение —
`local_search`, `local_index_status`, `local_read_file`; управление
индексацией (для агента) — `local_list_paths`, `local_add_path`,
`local_remove_path`, `local_set_email`, `local_trigger_rescan`. Управляющие
скрываются переменной `LQRAG_ALLOW_WRITE=0`. Диагностика моста пишется в
**stderr**.

### Авторегистрация в конфигах агентов

Юнит `lib-local-rag-mcp-register.service` прописывает мост при входе в сессию, а
`.path`-юниты повторяют это каждый раз, когда агент создаёт или перезаписывает
свой конфиг. Второе важно при тиражировании через СУС, где индексатор ставится
**до** приложения и приложение затирает запись.

| Агент | Файл | Схема |
|---|---|---|
| Workspace Computer | `~/.wsc/config/wsc.json` | `mcp.<имя>` |
| GigaCode | `~/.gigacode/settings.json` | `mcpServers.<имя>`: `command`, `args`, `env` |

`~` здесь — домашний каталог из passwd (`/home/ДОМЕН@ЛОГИН` на SberOS). У
терминала `$HOME` бывает другим (`/home/work/ЛОГИН@ДОМЕН`); скрипт пишет и
туда, если там есть каталог агента. Регистрацию делает и `postinst` при
установке, в уже открытых сессиях.

Посмотреть состояние:

```bash
python3 /usr/lib/lib-local-rag/mcp/register_mcp.py --doctor
```

Прописать вручную или проверить, что получится:

```bash
python3 /usr/lib/lib-local-rag/mcp/register_mcp.py --all
python3 /usr/lib/lib-local-rag/mcp/register_mcp.py --all --dry-run
```

Запись для Workspace Computer выглядит так:

```json
{
  "mcp": {
    "localrag": {
      "type": "local",
      "command": ["/usr/lib/lib-local-rag/mcp/mcp_launcher.sh"],
      "enabled": true,
      "timeout": 120000,
      "environment": { "LQRAG_TIMEOUT": "110" }
    }
  }
}
```

> Ключ внутри `mcp` — это **имя сервера**. Записи вида `mcp.servers.localrag` не
> существует: агент прочитает её как сервер с именем `servers`, не пройдёт
> валидацию и отбросит **весь** конфиг. Если такая запись осталась от старой
> версии пакета, `register_mcp.py` вычистит её сам.

**После регистрации агента нужно перезапустить** — конфиг читается на старте.

## 7. Типовые проблемы

**`systemctl --user status lib-local-rag-mcp-register.service` показывает
`inactive (dead)`.** Так и должно быть. Это `Type=oneshot`: юнит отрабатывает и
завершается. Смотрите на `status=0/SUCCESS` в строке `Process:`. Специально не
ставим `RemainAfterExit=yes` — с ним юнит остался бы `active`, а systemd не
перезапускает уже активный `Unit=` по срабатыванию `.path`, и перерегистрация
после перезаписи конфига перестала бы работать.

**В журнале пусто.** Почти всегда — `sudo journalctl --user`, см. раздел 3.
Если нет, смотрите файловый лог `~/.files-search/logs/lib-local-rag.log`.

**Ищу в логе `Uvicorn running` и не нахожу.** Этой строки не существует,
см. раздел 3.

**`curl` на `:8000` не отвечает.** Порт динамический, см. раздел 3.

**`Unit lib-local-rag.service could not be found` у пользователя.** Файл юнита
пользователю не читается: пакет собран в обход debhelper, без `dh_fixperms`, и
юниты легли с правами 0600. Так было с 1.0.6. Проверка:
`ls -l /usr/lib/systemd/user/lib-local-rag*` (нужно `-rw-r--r--`) и
`register_mcp.py --doctor`. Лечение — пакет, собранный через `make deb`,
поставленный поверх: его `postinst` исправит и права каталогов, оставшиеся от
старой версии.

**MCP-сервер не появился в интерфейсе агента.** По порядку:
1. агент перезапущен после регистрации?
2. `register_mcp.py --doctor` — запись на месте, файл читается, лаунчер
   доступен?
3. `ls -l /usr/lib/lib-local-rag/mcp/mcp_launcher.sh` — бит `+x` на месте?
4. `command -v python3` — интерпретатор виден из графической сессии?
5. `echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | .../mcp_launcher.sh`
   — мост отвечает сам по себе?

**Первый поиск после перезагрузки отвечает «индексатор запускается или
прогревается».** Демон греет модель 40-45 секунд, и пока прогрев не кончился,
API не отвечает. Живость демона мост определяет по `~/.files-search/pid`: процесс
жив — это прогрев, и systemd мост не трогает. Процесса нет — мост сам просит
systemd поднять `lib-local-rag.service` (не чаще раза в 3 минуты) и сразу
отвечает агенту, не дожидаясь прогрева. Повторный вызов через минуту даёт
результат. Если нет, смотрите `прогрев завершён за ...` в логе.

Другие ответы моста при недоступном демоне:

- «Служба LocalRAG временно остановлена: идёт установка или обновление
  пакета» — systemctl ответил, что юнит замаскирован: prerm маскирует службу
  (`mask --runtime`) на время замены файлов, postinst снимает маску;
- «Служба lib-local-rag.service недоступна для пользователя (не найдена)» —
  юнит не виден `systemd --user`, а живого демона нет;
- «Индексатор LocalRAG не поднимается (…)» — соединение отвергается подряд
  дольше 3 минут; в скобках `ActiveState`, `SubState`, `NRestarts` из
  `systemctl --user show lib-local-rag.service`. Дальше — журнал службы:
  `journalctl --user -u lib-local-rag.service`;
- «… Автозапуск: <причина>» — systemd поднять службу не смог (нет шины
  пользователя, нет systemctl, `LQRAG_AUTOSTART=0`), и прогрев мост не обещает.

**Конфиг агента потерял комментарии.** `register_mcp.py` читает JSONC, но пишет
обычный JSON. Исходный файл сохраняется рядом один раз, до первой правки:
`<файл>.localrag-backup`.
