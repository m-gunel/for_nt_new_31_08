# Подробная документация по проекту

## Общее описание

Проект представляет собой бэкенд-систему для индексации и поиска по локальным файлам и почте. Система анализирует документы, извлекает из них текст, создает векторные представления и позволяет выполнять семантический поиск по содержимому файлов.

Куда идти дальше:

- **новый разработчик** — [`docs/ONBOARDING.md`](docs/ONBOARDING.md): почему проект
  устроен именно так, что нельзя менять без обсуждения, какие доступы запросить;
- **тестировщик** — [`docs/HANDOVER.md`](docs/HANDOVER.md): поставить, запустить,
  прогнать НТ;
- **интеграция с агентом** — [`docs/mcp/README.md`](docs/mcp/README.md).

## Установка и запуск

### Установка

```bash
# Установка зависимостей
uv sync

# Если uv не установлен, установите его глобально
pip install uv --break-system-packages
```

Если `uv` недоступен, зависимости ставятся обычным pip:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Список зависимостей для pip лежит в `requirements.txt`, для сборки через uv — в
`[project.dependencies]` файла `pyproject.toml`. При изменении одного нужно
поправить и второй.

### Воспроизводимая установка

Версии в `pyproject.toml` и `requirements.txt` заданы через `>=` без верхней
границы, поэтому обычная установка берёт то, что лежит в зеркале сегодня. Для
приёмки и нагрузочного тестирования этого мало: между прогонами `lancedb` уехала
с 0.3x на 0.38, а это ядро хранения и поиска — сравнивать цифры на разных
версиях бессмысленно.

Поэтому состав фиксируется двумя файлами, которые коммитятся:

```bash
uv lock                                              # создать/обновить состав
uv export --no-hashes --format requirements-txt \
  --no-dev -o requirements.lock.txt                  # тот же состав для pip
```

Установка из зафиксированного состава:

```bash
uv sync --frozen                                     # uv
.venv/bin/pip install -r requirements.lock.txt       # pip
```

`requirements.txt` при этом остаётся человекочитаемым списком «что и зачем»,
а `requirements.lock.txt` — машинным слепком проверенного окружения.

Обновлять состав нужно осознанно (`uv lock --upgrade`) и перед прогоном НТ, а не
между ним и сборкой.

> **Лок генерируется только на рабочей машине.** `Dockerfile` подставляет
> реальный `OSC_TOKEN` прямо в `pyproject.toml` во время сборки, поэтому лок,
> созданный внутри сборки, унесёт живой токен в индексные URL. Перед коммитом
> проверьте: `grep -c OSC_TOKEN uv.lock` — должен находить плейсхолдер, а не
> подстановку.

## Запуск на АРМ с SberOS

Требуется Python 3.12 или новее (в коде используется синтаксис PEP 695:
`class LSMTable[T]`), права root не нужны — всё делается в папке проекта.

### 1. Подготовить окружение

```bash
python3 -V                      # ожидаем 3.12+
cd ~/lib-local-rag               # каталог, куда распакован проект
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/pip install -r requirements.txt
```

Если pip не достучится до репозитория пакетов (`Could not find a version...`
или таймауты), нужно указать внутренний индекс явно — адрес и токен взять
у своей команды, шаблон лежит в `pip.conf`:

```bash
.venv/bin/pip install -r requirements.txt \
  --index-url https://<пользователь>:<токен>@<внутренний-индекс>/simple
```

Проверить, что всё встало и модель грузится:

```bash
.venv/bin/python -c "
from src.utils.openvino_encoder import OpenVINOEmbedder
e = OpenVINOEmbedder('models/rubert-tiny2_002')
print('размерность:', e.encode(['проверка']).shape)"
```

Без каталога `models/rubert-tiny2_002` индексатор не стартует.

### 2. Подготовить конфиг

```yaml
# cfg/local.yml
file_scan_cfg:
  paths:
    - "~"          # весь домашний каталог; можно сузить до конкретных папок
embed_model_cfg:
  model_path: models/rubert-tiny2_002
email:
  enabled: false
app_logging_level: INFO
```

**Умолчание — весь домашний каталог** (`~`). Одна строка покрывает обе формы
имён в SberOS (`/home/work/ЛОГИН@sigma.sbrf.ru` и `/home/sigma.sbrf.ru@ЛОГИН`),
разбирать имя не нужно. Из обхода исключаются скрытые каталоги, `node_modules`,
`__pycache__`, `venv`, `site-packages`, `snap`, артефакты сборки — полный
список в `src/indexer/exclude.py`. Символьные ссылки обходятся
(`file_scan_cfg.follow_symlinks`, по умолчанию `true`), петли и повторный обход
одного дерева отсекаются по `(st_dev, st_ino)`, а в индекс попадает настоящий
путь, а не путь через ссылку. На сетевые монтирования (`nfs`, `cifs`, `autofs`
и прочие из `NETWORK_FS_TYPES`) обход не заходит.

**Ловушка:** сохранённый `~/.ragsearch/user_conf.yml` **перебивает**
`file_scan_cfg.paths` из YAML. На машине, где конфиг уже сохранён, правка YAML
не даст ничего — нужен `POST /api/v1/config` или удаление `user_conf.yml`.

Пути проверяются на существование, и недоступный корень попадает в лог
предупреждением с `errno`, а каждый путь — строкой «найдено файлов — N».
Раньше `os.scandir` на несуществующем каталоге молча пропускался, и типовая
ошибка (локализованное имя папки — `~/Документы` там, где каталог называется
`Documents`) выглядела как сломанный поиск, а не как пустой индекс. По ходу
обхода в лог идёт прогресс, а в конце — сводка со счётчиками пропусков
(по правам, по исключениям, на сетевых ФС, повторных).

Поверх наблюдения за файловой системой раз в `full_rescan_interval` секунд
(по умолчанию 3600, `0` — выключить) выполняется полный проход — **только в
простое**. Он подбирает то, что теряет inotify: события, отброшенные при
переполнении очереди, каталоги, ставшие читаемыми, и осиротевшие после
перемещений записи.

### 3. Запустить демон

```bash
CONFIG_PATH=cfg/local.yml RAG_PORT=8000 .venv/bin/python main.py
```

Переменные окружения:

| Переменная | Значение |
|---|---|
| `CONFIG_PATH` | путь к YAML-конфигу |
| `RAG_HOST` / `RAG_PORT` | адрес HTTP-сервера (по умолчанию `0.0.0.0:8000`) |
| `DEV=1` | индексы пишутся в `data/app` внутри проекта, а не в `~/.files-search` |
| `RESET=1` | удалить `~/.files-search` и `~/.ragsearch` перед стартом |
| `RAG_OV_NUM_THREADS` | потоков инференса OpenVINO (по умолчанию половина ядер; `0` — решает плагин). Старое имя `OV_NUM_THREADS` тоже работает |
| `RAG_OV_NUM_STREAMS` | streams OpenVINO (по умолчанию `2` — по числу каналов поиска и индексации; `0` — решает плагин) |
| `RAG_INDEX_THROTTLE_SECONDS` | пауза (сек) между батчами записи при индексации; `0` (по умолчанию) — без пауз |

Если на машине уже работает установленный из пакета индексатор, для проверочного
запуска задавайте `DEV=1` и свободный порт — иначе оба процесса будут писать
в одно хранилище.

### 4. Убедиться, что работает

```bash
curl http://127.0.0.1:8000/api/v1/health          # {"status":"OK"}
curl http://127.0.0.1:8000/api/v1/status          # files_to_index, is_indexing

# папки для индексации; почту включаем тем же запросом
curl -X POST http://127.0.0.1:8000/api/v1/config \
  -H "Content-Type: application/json" \
  -d '{"folders":["/home/sigma.sbrf.ru@SIGMA_LOGIN/Документы"],
       "email":{"enabled":true,"index_last_n_days":90}}'

# поиск по файлам (поведение по умолчанию)
curl -X POST http://127.0.0.1:8000/api/v1/search \
  -H "Content-Type: application/json" \
  -d '{"query":"отпуск","limit":5,"query_type":"hybrid"}'

# и по файлам, и по письмам — каждый источник получает свой limit
curl -X POST http://127.0.0.1:8000/api/v1/search \
  -H "Content-Type: application/json" \
  -d '{"query":"отпуск","limit":5,"sources":["files","email"]}'

# с фильтрами: docx и pdf из папки, изменённые в 2024, автор — Иванов
curl -X POST http://127.0.0.1:8000/api/v1/search \
  -H "Content-Type: application/json" \
  -d '{"query":"отпуск","filters":{"ext":["docx","pdf"],"folder":"/home/u/Документы",
       "modified_from":"2024-01-01","modified_to":"2024-12-31","author":"Иванов"}}'
```

### Что возвращает поиск

`limit` — число **документов**, а не чанков. Индексатор берёт из LanceDB пул
чанков на канал (`search_pool` в `src/indexer/indexer.py`: `limit × 5`, не
меньше 50 и не больше 500) и собирает из него документы: у каждого до трёх
лучших фрагментов, копии одного файла (одинаковый sha256) уходят в
`duplicates` и мест не занимают. Раньше `limit=10` давал 10 чанков — в
среднем 6 документов.

- **Карточка документа.** К чанкам каждого документа индексатор добавляет
  строку `kind="card"`: имя файла, название, автор, тема, ключевые слова.
  Она находит файл по имени и свойствам, но фрагментом в выдачу не идёт.
  Если она совпала с запросом словами (FTS-канал `hybrid` и `text`),
  документ получает отметку `match: ["card"]`. Индексу, собранному до
  карточек, их дописывает первый проход индексации после обновления
  (`migrate_document_cards`: из meta уже в индексе, без разбора файлов) —
  сбрасывать индекс не нужно.
- **Код из имени файла.** Слово запроса с цифрой и буквой или `_`
  («ЦБ_21», «ЦБ_21.pdf», «5348-У», «obs_286»), совпавшее целым словом с
  именем 1–3 документов (копии с одним sha256 — один документ), ставит эти
  файлы первыми (`match: ["name_code"]`), даже если их нет в пуле; их `score`
  тогда `null`. Годы и голые числа кодом не считаются.
- **Фильтры** (`filters`): `ext`, `folder` (поддерево), `modified_from` /
  `modified_to`, `created_from` / `created_to` (даты, включительно; дата из
  свойств документа, без неё — файла на диске), `author` (автор или
  последний редактор, подстрока без учёта регистра и разницы ё/е).
  Строки отбираются до пула, во всех `query_type`. Все фильтры
  необязательны: без `filters` ищется весь индекс, пустое поле (`""`, `[]`)
  — то же, что его нет. В Swagger (`/docs`) у запроса два готовых примера —
  без фильтров (подставляется сразу) и с ними.

### Источники поиска

Файлы и письма лежат в **разных таблицах** LanceDB, и `POST /search` по
умолчанию ищет только по файлам (`sources: ["files"]`).

Так сделано потому, что пул чанков (`.limit()` LanceDB) берётся по таблице: в
общей таблице ящик в десятки тысяч писем просто вытесняет документы из
выдачи — коротким почтовым чанкам вдобавок помогает нормализация длины в
BM25. Разделение убирает и вторую проблему: у каждой таблицы свой IVF-PQ,
обученный на своём размере и своём распределении.

При `sources: ["files","email"]` каждый источник ищется отдельно и получает
свой `limit` документов, поэтому письма не занимают места файлов. Оценки
между таблицами сравнимы только для `query_type: "vector"` (косинусное
расстояние); для `text` (BM25 считает IDF по своему корпусу) и `hybrid` (RRF считается внутри
одного запроса) порядок между источниками — чередование по рангу, а не общий
ранжир. Внутри источника порядок честный.

Индекс, собранный до разделения, мигрируется автоматически при старте: строки
писем **переносятся** из таблицы файлов в почтовую вместе с уже посчитанными
векторами, без повторного инференса, после чего индексы таблицы файлов
пересобираются. Повторный старт ничего не делает.

`folders` проверяется на существование: несуществующий путь получает **400**, и
конфиг на диске не меняется. Это защита от тихой поломки — сохранённый мусорный
путь (например, значение `string`, которое по умолчанию подставляет Swagger) не
находит файлов и роняет наблюдение за файловой системой целиком.

Не заполняйте в Swagger поле `email.offsets` — это отладочная ручка, состояние
чтения mbox живёт в `~/.files-search/offsets.json`. Имена папок, которых нет на
диске, демон пропускает с предупреждением.

Первая индексация занимает время: модель грузится около 30 секунд, дальше
скорость зависит от объёма корпуса. Прогресс виден в `/api/v1/status` и в логе.

### 5. Остановить

`Ctrl+C` в терминале демона — на остановку индексатора отводится 5 секунд.
Индексы остаются на диске и при следующем запуске переиспользуются.

### Если что-то не работает

- **`SyntaxError` при импорте** — Python старше 3.12.
- **`.doc`-файлы пропускаются** — на машине нет ни `catdoc`, ни `antiword`,
  ни `soffice`. Остальные форматы при этом индексируются.
- **watcher не замечает новые файлы** — проверить лимит inotify:
  `cat /proc/sys/fs/inotify/max_user_watches`. При большом числе отслеживаемых
  каталогов события теряются.
- **`free disk space is less then 1GiB`** — индексация не стартует, пока на
  разделе с `~/.files-search` меньше 1 ГБ свободного места.

## Поставка пакетом (.deb)

БТ библиотеки индексации §4.1 требует предустановленного системного пакета.
Пакет собирается из **готового** `dist/`, своей сборки у него нет:

```bash
make build        # или make docker_build, как в CI
make deb          # dpkg-buildpackage (debhelper), затем scripts/check_deb.sh
```

**Собирать только через `make deb`.** На рабочих ноутбуках umask 077, и ручная
сборка (`tar`+`ar`, `dpkg-deb -b`) переносит в пакет права исходников 0600/0700.
Юниты с правами 0600 root включает, а `systemd --user` пользователя открыть не
может: «Unit lib-local-rag.service could not be found», MCP не прописан. Так
вышел 1.0.6. debhelper выравнивает права (`dh_fixperms`), а
`scripts/check_deb.sh` проверяет готовый пакет. Варианты сборки (CI, Docker,
нативно) — [debian/README.md §2](debian/README.md).

Что раскладывает пакет:

| Путь | Содержимое |
|---|---|
| `/opt/lib-local-rag/` | бинарь демона со вшитой моделью |
| `/usr/lib/lib-local-rag/mcp/` | MCP-мост, лаунчер, `register_mcp.py` |
| `/usr/lib/lib-local-rag/uninstall.sh` | полная очистка пользовательских данных |
| `/etc/lib-local-rag/distro.yml` | конфиг демона |
| `/usr/lib/systemd/user/lib-local-rag.service` | пользовательский юнит демона |
| `/usr/lib/systemd/user/lib-local-rag-mcp-register.service` | регистрация MCP в конфигах агентов |
| `/usr/lib/systemd/user/lib-local-rag-mcp-register-*.path` | перерегистрация, когда агент переписал конфиг |

Юнит **пользовательский**, а не системный: демон обязан работать с правами
владельца файлов, иначе упрётся в права на домашние каталоги. Он запускает
демон с `RAG_HOST=127.0.0.1` и `RAG_PORT=0` — порт выбирает ядро и публикует
в `~/.files-search/port`, откуда его читает MCP-мост.

Ставится `sudo dpkg -i lib-local-rag_<версия>_amd64.deb`, в том числе поверх
предыдущей версии без удаления.

`postinst` юниты **включает** — это делает вставка `dh_installsystemduser` через
маркер `#DEBHELPER#`: она кладёт симлинки в `/etc/systemd/user/default.target.wants/`,
то есть сразу для всех пользователей системы, и запущенный systemd для этого не
нужен (что и требуется при сборке образа ОС). В каждом юните стоит
`ConditionUser=!@system`: у root, greeter-а и других системных учёток юниты не
стартуют, иначе root с `paths: /home` проиндексировал бы чужие файлы.

Дальше `postinst` открывает для всех права своих каталогов и юнитов (так
лечится обновление с 1.0.6, где они легли с 0700: сам dpkg права существующих
каталогов не меняет). В уже открытых сессиях он поднимает юниты: для каждого
пользователя `runuser` и `systemctl --user` через приватный сокет его
менеджера (`XDG_RUNTIME_DIR=/run/user/<uid>`), без D-Bus и PAM-входа. Там же
сразу прописывает MCP и в конце печатает итог по каждому пользователю: поднят
ли демон и куда прописан мост. Подробности — [debian/README.md §4](debian/README.md).

Регистрацию MCP-моста в конфигах агентов, кроме `postinst`, делает
**пользовательский** юнит `lib-local-rag-mcp-register.service` при каждом входе.
Всё это работает от имени пользователя: запись от root досталась бы root, и
агент не смог бы её переписать; вдобавок при сборке образа домашних каталогов
ещё не существует. Парные `.path`-юниты повторяют регистрацию, когда агент
создаёт или перезаписывает свой конфиг. Скрипт пишет в домашний каталог из
passwd и, если там есть каталог агента, в `$HOME` терминала (на SberOS это
разные каталоги: `/home/ДОМЕН@ЛОГИН` и `/home/work/ЛОГИН@ДОМЕН`).

Включённый юнит сразу запускает индексацию: в `distro.yml` стоит
`autostart_indexing: true`, поставка бесшовная. Остановить на сессию —
`POST /api/v1/deactivate`; состояние не персистится, после перезапуска демона
индексация возобновляется, так что хранить его демону не нужно.

`apt remove` оставляет индексы (переустановка не потребует собирать их заново,
а это часы на большом корпусе). `apt purge` останавливает демон, сносит
`~/.files-search` и `~/.ragsearch` у всех реальных пользователей, чистит
временные выдачи и печатает уведомление — это БТ §7.

## Конфигурация

Основная конфигурация находится в `cfg/dev.yml`. Основные параметры:

- `embed_model_cfg.model_path` - путь к модели эмбеддингов (по умолчанию `models/rubert-tiny2_002`)
- `file_scan_cfg` - параметры сканирования файлов
  - `paths` - пути для сканирования
  - `allowed_extensions` - разрешенные расширения файлов
  - `max_size` - максимальный размер файлов для обработки

Конфигурация может быть переопределена через переменные окружения или внешние файлы конфигурации.
Переменные окружения для полей конфига требуют префикса `RAG_`: например `RAG_APP_LOGGING_LEVEL=DEBUG`
задаёт `app_logging_level`. Без префикса переменные игнорируются.

## API и интерфейс

После запуска сервера доступен Swagger UI по адресу
[http://localhost:8000/docs](http://localhost:8000/docs) (из пакета — на порту из
`~/.files-search/port`), где можно ознакомиться с API и протестировать его методы.

### Swagger в закрытом контуре

Штатный `/docs` подгружает `swagger-ui-bundle.js` и `swagger-ui.css` с
`cdn.jsdelivr.net`. Там, где интернета нет, страница отдаётся с кодом 200 и
открывается **пустой** — без ошибки в логе и без подсказки, что случилось.

Приложение это умеет обходить: если в `src/server/static/` лежат
`swagger-ui-bundle.js` и `swagger-ui.css`, они раздаются локально, и страница
работает без сети. Если файлов нет — поведение прежнее, через CDN, а в лог при
старте уходит предупреждение. Как получить файлы и куда положить — см.
[src/server/static/README.md](src/server/static/README.md).

### Основные эндпоинты

- `GET /api/v1/health` - проверка работоспособности сервиса
- `POST /api/v1/search` - выполнение поискового запроса (по умолчанию — только
  по файлам, см. «Источники поиска»)
- `GET /api/v1/status` - получение статуса индексирования (поле `active`
  отличает «индексация выключена» от «простаиваю»)
- `GET/POST /api/v1/config` - управление конфигурацией (выбор папок для индексации)
- `POST /api/v1/activate` - включить индексацию
- `POST /api/v1/deactivate` - остановить индексацию, сохранив индексы
- `POST /api/v1/reset` - сброс до состояния «как после установки»
  (`?keep_config=true` оставит список папок)

### Управление индексацией

Ручки deactivate/reset — пульт кодингового агента: без них остановить
индексацию можно было только убийством процесса, а сбросить — только
перезапуском с `RESET=1`.

Индексация стартует вместе с процессом — это штатный режим поставки, отдельно
включать нечего. Обратный вариант — отладочный: `autostart_indexing: false`
в конфиге или `RAG_AUTOSTART_INDEXING=0`, когда демон должен подниматься, но
не трогать файлы до явной `POST /api/v1/activate`.

Ручки идемпотентны: повторная активация не прерывает идущий проход, повторная
деактивация не ошибка. Поле `changed` в ответе показывает, изменилось ли
состояние.

## Архитектура проекта

### Основные компоненты

#### `main.py`

Точка входа в приложение. Инициализирует конфигурацию, настраивает логирование и запускает FastAPI-сервер.

#### `src/config.py`

Содержит класс `Config`, управляющий всей конфигурацией приложения. Использует Pydantic BaseSettings для загрузки конфигурации из YAML-файлов, переменных окружения и других источников.


Основные настройки:
- `EmbeddingModelConfig` - конфигурация модели для создания эмбеддингов
- `FileScanConfig` - конфигурация сканирования файлов
- `SplitterCfg` - конфигурация разбиения текста на чанки

#### `src/server/`

Содержит компоненты серверной части:

- `app.py` - инициализация FastAPI приложения с менеджером жизненного цикла
- `router.py` - определение маршрутов API
- `model.py` - Pydantic-модели для запросов и ответов

#### `src/indexer/`

Модуль индексирования файлов:

- `indexer.py` - основной класс `Index` для управления процессом индексирования
- `scan_dir.py` - функции для рекурсивного сканирования директорий
- `exclude.py` - паттерны исключения для файлов и директорий (например, `.venv`, `node_modules`)
- `scanners/` - сборщики файлов и писем в очередь на индексацию
- `watcher/` - наблюдение за изменениями в файловой системе

#### `src/parsers/`

Парсеры для различных форматов файлов:

- `pdf.py` - парсер PDF-файлов с использованием `pymupdf`
- `docx.py` - парсер DOCX/DOC-файлов
- `pptx.py` - парсер PPTX-файлов
- `xlsx.py` - продвинутый парсер Excel-файлов с эвристиками для определения заголовков и фильтрации листов

#### `src/common/`

Общие модели данных:

- `models.py` - общие Pydantic-модели
- `doc_meta.py` - модели метаданных файлов и чанков

#### `src/utils/`

Вспомогательные утилиты:

- `lance_wrapper.py` - обертка для работы с LanceDB (векторная база данных)
- `openvino_encoder.py` - класс `OpenVINOEmbedder` для кодирования текста в эмбеддинги с использованием OpenVINO
- `batch_embeddings.py` - утилиты для пакетной обработки эмбеддингов

#### `src/malloc_tuning.py`

Настройки аллокатора glibc (лимит арен и `malloc_trim`), ограничивающие рост RSS
многопоточного демона. Вне glibc — no-op.

## Работа с данными

### Индексация файлов

Процесс индексации включает следующие этапы:

1. Сканирование указанных директорий на наличие файлов
2. Проверка метаданных файлов (размер, время изменения) для определения необходимости перепроиндексации
3. Извлечение текста из файлов с помощью соответствующих парсеров
4. Разбиение текста на чанки с помощью `RecursiveCharacterTextSplitter`
5. Создание векторных представлений (эмбеддингов) для чанков
6. Сохранение чанков и эмбеддингов в базу данных

Используются два механизма хранения:

- **LSM-дерево** (через библиотеку `lsm`) - для отслеживания состояния файлов и очереди на индексацию
- **LanceDB** - для хранения векторных представлений и выполнения поиска

### Расположение данных

- `~/.files-search/lance/` - векторный индекс LanceDB: таблица `files`
  (документы) и таблица `files_email` (письма и вложения), у каждой свои
  FTS- и IVF-PQ-индексы
- `~/.files-search/indexed.lsm` - состояние файлов (путь → размер, mtime)
- `~/.files-search/files/`, `~/.files-search/emails/` - очереди на индексацию
  (persistqueue), `~/.files-search/offsets.json` - позиции чтения mbox
- `~/.ragsearch/user_conf.yml` - пользовательская конфигурация (список папок, почта)

При `DEV=1` всё перечисленное живёт в `data/app` внутри проекта
(`~/.ragsearch` остаётся на месте).

### Индексация почты (Thunderbird)

- Почта **выключена по умолчанию**. Включается запросом
  `POST /api/v1/config` с телом `{"email":{"enabled":true}}` — без рестарта
  демона, первый проход стартует сразу. Выключение (`enabled:false`) **удаляет
  почтовый индекс целиком** (дроп таблицы `files_email`), поэтому повторное
  включение — индексация с нуля. Таблица файлов при этом не затрагивается.
- Окно индексации по умолчанию — `index_last_n_days: 30`. Раньше умолчанием
  было `null`, то есть весь ящик за все годы: клиент, приславший
  `{"email":{"enabled":true}}` без этого поля, молча получал индексацию всей
  переписки. Явный `null` по-прежнему снимает ограничение.
- Ограничения размера (`email_scan_cfg` в конфиге):

  | Параметр | По умолчанию | Что делает |
  |---|---|---|
  | `max_message_size` | 48 МиБ | письмо крупнее не читается и не индексируется |
  | `max_attachment_size` | 30 МиБ | вложение крупнее пропускается, тело письма индексируется |

  Порог письма обязан быть выше порога вложения: вложение едет внутри письма в
  base64, то есть занимает примерно на треть больше. Пропуски видны в логе:
  `mbox прочитан за N c — X писем в очередь, Y пропущено по дате, Z пропущено по размеру`.
- За метаданными письма читается только блок заголовков, а не письмо целиком —
  иначе ящик с вложениями на десятки мегабайт давал соответствующие скачки RSS.
- Почтовый корень ищется по каталогу `ImapMail/<host>` в `~/.thunderbird`
  (предпочитается `imap.sberbank.ru`); явный путь можно задать через
  `email.path_to_email_folder` в `POST /api/v1/config` — тогда автопоиск
  не выполняется. Это же позволяет индексировать любые mbox-каталоги без
  Thunderbird (используется тестами).
- Почту можно включить и выключить через `POST /api/v1/config` без рестарта
  демона; `POST /config` — частичный апдейт, не присланные поля не
  затираются.
- Состояние папок хранится в `offsets.json` (формат v2: offset + size +
  mtime mbox на момент последнего прохода). Неизменившиеся папки на
  поллинге не читаются вовсе.
- Компакция mbox (Thunderbird переписывает файл при окончательном удалении
  писем — все байтовые offset'ы сдвигаются) детектируется по уменьшению
  файла и по сбитой `From `-границе; папка при этом переиндексируется с
  нуля, чанки удалённых писем уходят из индекса.
- Отсутствующий локально mbox (например, «Входящие» не синхронизированы)
  просто пропускается и не мешает индексации файлов.

### Диагностика на АРМ SberOS

`python3 scripts/sberos_check.py` — самодостаточный скрипт (только stdlib):
проверяет профиль Thunderbird, состояние offsets, скорость обхода mbox,
inotify-лимиты, живость API и укомплектованность PyInstaller-сборки. Отчёт
пишется в `sberos_report.json` и не содержит персональных данных. Режим
`--compaction before|after` снимает снимки до и после компакции.

### Поддерживаемые форматы файлов

- PDF
- DOCX, DOC
- PPTX
- XLSX (XLS зарегистрирован, но openpyxl его фактически не читает)
- TXT

Фактический список задаёт реестр парсеров (`@parser(...)` в `src/parsers/`), а не
поле `file_scan_cfg.allowed_extensions` — оно не используется. Парсера для `.md`
пока нет, хотя БТ его называет.

### Модель эмбеддингов

Проект использует модель `rubert-tiny2` для создания векторных представлений текста. Модель оптимизирована для работы с OpenVINO, что позволяет выполнять инференс на CPU без необходимости в GPU.

## Особенности реализации

### Асинхронная архитектура

Проект построен с использованием асинхронных подходов:

- Асинхронное сканирование директорий
- Асинхронная обработка файлов
- Асинхронные операции с базой данных

### Оптимизация ресурсов

- Ограничение потребления CPU через настройки OpenVINO: по умолчанию инференсу
  отдаётся половина ядер машины, переопределяется через `RAG_OV_NUM_THREADS`
  (старое имя `OV_NUM_THREADS` поддерживается)
- **Два stream'а инференса** (`RAG_OV_NUM_STREAMS`, по умолчанию 2) — ровно по числу
  каналов, поиска и индексации. Stream — единица параллелизма плагина, и одного на
  оба канала мало: потоки Python есть, а исполняются они по очереди, поэтому живой
  поисковый запрос ждёт окончания текущего батча индексации. Второй stream снимает
  это почти полностью, ценой около 10% скорости индексации и десятков мегабайт RSS.
  `THROUGHPUT` для этой задачи не годится — плагин дробит пул по одному потоку на
  stream, и индексация замедляется в разы
- Ограничение числа арен glibc и возврат страниц ОС через `malloc_trim`
  (`RAG_MALLOC_ARENA_MAX`, `RAG_MALLOC_TRIM`)
- Понижение приоритета (`nice +10`) для потоков индексации, парсинга и перестройки
  индексов; канал поиска намеренно остаётся с обычным приоритетом (`src/utils/thread_priority.py`,
  вне Linux — no-op)
- Постановка наблюдения за файловой системой выполняется в отдельном потоке: для
  inotify это обход всего дерева с системным вызовом на каждый каталог, и в event loop
  он блокировал бы `/health`, `/status` и `/search`
- Управление памятью с периодической очисткой кэшей
- Проверка свободного места на диске перед индексацией

### Обработка ошибок

Система устойчива к различным ошибкам:

- Поврежденные файлы
- Отсутствующие файлы
- Ошибки при парсинге
- Недостаток дискового пространства

## Тесты

```bash
uv run pytest -m "not integration"
```

Без `uv` — тестовые зависимости ставятся отдельно (в `requirements.txt` их нет:
он только для запуска демона):

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -m "not integration"
```

Прогон должен быть зелёным целиком. Под маркером `integration` идут тесты,
которым нужно внешнее окружение — реальный профиль Thunderbird и поднятый
демон; они исключаются флагом `-m "not integration"` и запускаются отдельно:

```bash
uv run pytest -m integration
```

Тесты MCP-моста (`tests/test_mcp_protocol.py`, `tests/test_mcp_tools_contract.py`)
идут в общем прогоне: они работают на заглушке сайдкара и не требуют ни индекса,
ни OpenVINO.

Тесты не читают личные данные: почтовые проверки идут на синтетических
mbox-фикстурах (`tests/mbox_fixture.py`), а `~/.ragsearch` и `~/.files-search`
подменяются на временные каталоги (`DEV=1` выставляется в `tests/conftest.py`).

### Проверка на АРМ с SberOS

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt
.venv/bin/python -m pytest -m "not integration" -q     # ожидается зелёный прогон
python3 scripts/sberos_check.py                        # диагностика окружения
```

`sberos_check.py` — только stdlib, ставить ничего не нужно. Он проверяет профиль
Thunderbird, состояние почтовых офсетов, скорость обхода mbox, лимиты inotify,
живость API и укомплектованность PyInstaller-сборки. Отчёт пишется в
`scripts/sberos_report.json` и **не содержит персональных данных**: ни тем и тел
писем, ни адресов, ни имён личных папок (нестандартные имена заменяются хешем).
